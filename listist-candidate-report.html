Listist is a weak fit for Wycinanka's option lists; its real gap is card-id identity outside lessons

I found about 22 distinct closed lists. 11 of them are written down in three or more layers (validation schema, app code, display, content, docs). 5 show verified drift: values, labels or a stale copy. None of that drift is a live bug today: every disagreement is a gap or a stale document, not a failing request. The most valuable place for Listist-style discipline is not a dropdown. It is the identity of review cards. Lesson cards already have an append-only id ledger, but frequency-word, picture and phrase cards don't, and learners' FSRS history is stored against those ids. The one strong reference-data candidate is CEFR levels, which already exist as the public list public:i18n.cefr-levels@v1.

Sources: the Listist agent handbook (/api/v1/begin, fetched live 2026-10-06, consistent with the skill's summary); public catalogue search and tag queries. In the repo I searched src/, migrations/, public/ scripts and manifest, scripts/, test/, e2e/, docs/, README, index.html, and git history using ripgrep and git log -S.

Listist in this codebase's terms

Keep each list once

The speaker value 'm' | 'f' is typed out inline 11 times: schemas.ts:37, voices.ts:11, speaking.ts:35, four times in exercises.ts, Lesson.tsx:191, reading.ts:62,74 and Profile.tsx:264. CEFR level labels are copied in Learn.tsx:14 and Reading.tsx:29.

Pin immutable versions

The cards table stores a bare card_id with no content version. The meaning of an id is protected only by test/unit/card-ids.json, and only for lesson cards.

Values are identity

Mostly respected: unit ids come from a fixed key, not position (build.ts:72). Exceptions: some card ids are derived from Polish text (chunk-${slug(p)}, f:${slug(pl)}), and the "A0" level is decided by position, u.n === 0 (badges.ts:53,89, Learn.tsx:47).

Retire, never delete

Strength legacy-ids.ts ("Never edit this file") and the card-ids.json ledger refuse removed or moved ids. Corrections keep their old ids through key (commit 49fd35b). There is no replacedBy equivalent: an accepted reset simply adds a new id.

People curate, agents read

No agent writes option values. Whisper output (speech.ts:17) is only compared with expected text. Content corrections are made by people (and by AI-assisted commits) and reviewed in PRs.

Never auto-upgrade a pin

The app bundles all content, so every deploy is a "head" upgrade for stored card ids. The ledger test is the only check that stops an upgrade from changing what an id means.

Look up raw strings

No vocabulary import exists. The text normalisers (grade.ts, speaking.ts:35) grade Polish answers; they don't map raw strings to option values.

Do not invent values

Values are typed inline in TSX (Profile.tsx:153 goals [10, 20, 30, 50], Profile.tsx:250 themes) and must match schemas.ts by hand.

1. Review-card catalogue

catalogueGap
Copies

Content: build.ts:41-54, frequency.ts:520, pictures.ts:31, chunks.ts:35. Registry: course.ts:42-58 (cardMap). Ledger: legacy-ids.ts, test/unit/card-ids.json (1,400+ entries). DB: cards.card_id. Server check: engine.ts:91 isCardId. Audio: public/voice-index.json (hash of text).

Drift

The ledger covers lessons only. Word, picture and phrase ids depend on text and order. No version is stored with a card, and there is no "retired, replaced by" record. A reset just adds a new id, and the old card stays in the learner's deck as an unknown id that engine.ts:91 refuses.

What Listist changes

One versioned source for card ids, with retirement and replacedBy. Stored cards could carry the catalogue version. This only pays off if the catalogue gets consumers beyond this app's bundle.

Existing public list

None found (course-specific).

Proposed id

org:wycinanka:course.cards

Rough cost

High. More than 1,400 ids, content authored in TypeScript, and an offline-first PWA that needs a bundled copy anyway. Extending the existing ledger idea to the other card kinds covers most of the value for less.

Agents and prompts

No runtime agent or prompt writes option values. The only model at runtime is Whisper on Workers AI (routes/speech.ts:17), which transcribes speech that is then graded against fixed text. Nothing is stored. The repository has no prompt templates or tool definitions. Content corrections have been made with AI assistance through reviewed commits (for example 49fd35b). That is where an agent could change a card's text and so its meaning, and the ledger test is the guard. docs/PLAN.md names no planned AI features that would need validated option values.

Where not to use Listist

  • Tenant and record data: usernames, sessions, push endpoints, per-user cards and activity.
  • Algorithm constants: FSRS rating 1..4 and card state 0|1|2 (fsrs.ts:9-12). They are governed by the algorithm. The labels in Session.tsx:551-554 say "Forgot" where the source comment says "Again", which is cosmetic.
  • UI state machines: Phase, Stage, Engine, InstallMode, listen errors.
  • Design tokens: badge tones (badges.ts:16 and the CSS variables), theme colours.
  • Single-source content enums already typed once: culture themes (culture.ts:8,52), speaking modes (speaking.ts:32, Speaking.tsx:13), password problems (password.ts:21,33).
  • Time zones: validated by pattern and IANA, not a closed list the app owns.

Decisions needed

  • Close the six gaps above directly, without Listist? Most of them are a matter of shared types.
  • Should frequency-word, picture and phrase card ids get the same append-only protection as lesson cards?
  • Is "A0" a real level for this course? If so, should it be declared as a value, or as an extension of the public CEFR list (request it from a person in the portal)?
  • Speaker gender and voice both use m|f: one list or two declared lists?
  • Is there any consumer of this course's content outside the bundled app (another app, an export, an agent)? Without one, Listist's version pinning adds little over the existing ledger.
  • Should docs/PLAN.md section 4.2 be updated or marked historical?
